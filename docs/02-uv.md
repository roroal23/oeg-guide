# uv: gestión de proyectos y dependencias

**uv** es un gestor de paquetes y de proyectos de Python escrito en Rust por Astral, los autores de `ruff`. Reúne en una sola herramienta lo que antes hacían `pip`, `venv`, `pip-tools` y `pyenv`:

- **Gestiona versiones de Python** (como `pyenv`), **entornos virtuales** (como `venv`) y **dependencias** (como `pip`).
- **Es muy rápido.** Usa una caché global y enlaces a ella, así que recrear un entorno que ya instalaste antes tarda segundos, incluso con PyTorch o vLLM.
- **Es reproducible.** Resuelve las dependencias una vez y guarda el resultado exacto en `uv.lock`; cualquiera que clone el proyecto, en otro PC o en Magerit, obtiene exactamente las mismas versiones.

**En este repositorio todos los proyectos usan uv.** Cada carpeta de proyecto es un proyecto uv independiente.

## Anatomía de un proyecto uv

| Fichero | Qué es | ¿Se edita a mano? | ¿Va a git? |
|---|---|---|---|
| `pyproject.toml` | El manifiesto: nombre, versión de Python admitida (`requires-python`) y dependencias directas. Sustituye al `requirements.txt`. | Sí (o con `uv add`) | Sí |
| `uv.lock` | Todas las dependencias, incluidas las indirectas, con versión exacta y hash. Lo genera uv. | **No** | Sí |
| `.python-version` | La versión de Python del proyecto (p. ej. `3.11`). uv la usa para elegir intérprete. | Sí | Sí |
| `.venv/` | El entorno virtual con las librerías instaladas. Es desechable: `uv sync` lo reconstruye. | No | **No** |

## Comandos del día a día

```bash
uv init mi_proyecto            # crea pyproject.toml, .python-version, main.py y README.md
uv init --python 3.11 mi_proy  # lo mismo, fijando la versión de Python

uv add transformers datasets   # añade dependencias (actualiza pyproject.toml y uv.lock e instala)
uv add "vllm==0.26.0"          # fija una versión concreta
uv add --dev ipykernel         # dependencia solo de desarrollo (grupo dev)
uv remove datasets             # la quita

uv sync                        # crea o actualiza .venv/ para que coincida exactamente con uv.lock
uv run main.py                 # ejecuta dentro del entorno (sincroniza antes si hace falta)
uv run python -m paquete.modulo
uv run --with jupyter jupyter lab   # herramienta puntual sin añadirla al proyecto

uv lock --check                # ¿pyproject.toml y uv.lock están de acuerdo?
uv tree                        # árbol de dependencias
uv pip list                    # paquetes instalados en .venv
```

> [!TIP]
> Con `uv run` no hace falta activar el entorno (`source .venv/bin/activate`). Si prefieres activarlo, también funciona.

Ejemplo de lo que crea `uv init`:

```bash
usuario@PC:~/proyectos$ uv init litellm-mock
Initialized project `litellm-mock` at `/home/usuario/proyectos/litellm-mock`
usuario@PC:~/proyectos$ tree -a litellm-mock
litellm-mock
├── main.py
├── pyproject.toml
├── .python-version
└── README.md
```

Para crear un proyecto que además traiga los scripts de SLURM y la carpeta `logs/`, usa [`templates/init_project.sh`](../templates/init_project.sh).

## uv en Magerit

### Instalación (una vez)
uv se instala en tu `$HOME` sin permisos de administrador:

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh   # lo deja en ~/.local/bin
uv --version
```

### Cachés fuera del `$HOME`
La cuota del directorio personal es pequeña, y tanto la caché de uv como los modelos de Hugging Face ocupan muchos GB. Las plantillas exportan:

```bash
PROJECT_DIR="$(dirname "$HOME")/PROJECT"          # /home/<code>/PROJECT
export UV_CACHE_DIR="${PROJECT_DIR}/.cache/uv"
export HF_HOME="${PROJECT_DIR}/.cache/huggingface"
```

Si uv avisa de que no puede usar *hardlinks* porque la caché y el proyecto están en sistemas de ficheros distintos, añade `export UV_LINK_MODE=copy`.

### Versión de Python: módulo frente a Python gestionado por uv
Hay dos formas de conseguir el intérprete:

1. **Cargar el módulo que coincide con `.python-version`** (lo que hacen nuestras plantillas): `module load Python/3.11.3-GCCcore-12.3.0` para proyectos en 3.11, o `Python/3.12.3-GCCcore-13.3.0` para 3.12. uv encuentra ese intérprete en el `PATH` y lo usa. El módulo de Python también trae su `GCCcore`, y vLLM necesita un compilador de C para compilar *kernels* al arrancar.
2. **Dejar que uv lo descargue** (`uv python install 3.11`). Es un Python autocontenido que evita problemas como el de `libpython` descrito en [01-magerit.md](01-magerit.md#miscelánea), pero no lo hemos probado a fondo en los nodos de cálculo.

Lo importante es que **no se mezclen**: si `.python-version` dice 3.11 y cargas el módulo 3.12, uv descargará otro Python o fallará.

### Flujo de trabajo
1. En local: `uv add ...`, programar y probar. Se suben `pyproject.toml`, `uv.lock` y `.python-version`.
2. En Magerit (`git pull` o `scp`), desde la carpeta del proyecto: `sbatch prepare_job.sh`, que ejecuta `uv sync` en la partición `debug`, sin GPU.
3. `sbatch execute_job.sh`, que ejecuta `uv run ...` en una partición con GPU.

Más detalle en [03-local-to-magerit-workflow.md](03-local-to-magerit-workflow.md).

## Los dos «stacks» de este repositorio

No hay un entorno común para todo el repo: cada proyecto tiene su propio `pyproject.toml` y su `uv.lock`. Así cada uno se puede copiar y ejecutar por separado, y actualizar las dependencias de uno no rompe otro. En la práctica hay dos familias:

| Stack | Python | Versiones clave | Proyectos |
|---|---|---|---|
| **vLLM en Magerit** | 3.11 | `vllm==0.26.0` (trae `torch` 2.11 para CUDA 13 y `transformers` 5.x) | `03_vllm/*` |
| **Local / CPU** | 3.12 | Las últimas versiones | `01_fundamentals`, `02_ollama-and-rag`, `04_huggingface`, `05_evaluation` |

Las particularidades de vLLM (GPU, flags, versiones) están en [04-vllm-on-magerit.md](04-vllm-on-magerit.md).
